# Skillstate Plan

## Summary

Skillstate is a lightweight, declarative dependency manager for AI agent skills. It reads project intent from `skillstate.toml` and delegates discovery and installation to the established [`skills`](https://github.com/vercel-labs/skills) CLI.

The goal is not to build another skill installer or registry. Skillstate adds the package-manager workflow currently missing from `skills`: a human-owned manifest, repeatable synchronization, safe reconciliation, and CI validation.

```text
skillstate.toml  ->  skillstate planner  ->  skills CLI  ->  agent skill directories
                              |
                              +-> skills-lock.json
```

## Product Positioning

> Declarative skill environments, powered by skills.sh.

Skillstate should feel familiar to users of `uv`, Poetry, npm, and Terraform:

- Declare desired dependencies in a reviewable manifest.
- Install the same project skills with one command.
- Preview changes before mutation.
- Detect drift in CI.
- Update dependencies intentionally.
- Let the underlying ecosystem own source discovery and agent compatibility.

### Differentiation

Existing tools prove demand but leave a specific gap:

| Tool | Useful idea | Gap relative to Skillstate |
| --- | --- | --- |
| `skillpack` | TypeScript wrapper around `skills` | YAML, stale hardcoded agents, fake timestamp lock, no full reconciliation |
| `skills-manifest` | Declarative wrapper | JSON, mutates `node_modules/skills`, weak lock semantics |
| `agr` | TOML and commit-based lock | Python, separate installer, limited agents, effectively dormant |
| `skillfile` | Declarative installs and exact revisions | Rust, custom format, separate installer |
| `skills-lock` | Strong frozen/integrity model | `package.json` manifest, separate installer |
| `skillkit` | Broad manifest-driven ecosystem | Large independent platform rather than thin `skills` frontend |

Skillstate's narrow promise:

1. TypeScript CLI runnable through `npx`.
2. TOML manifest designed for humans and code review.
3. `skills` remains the installation backend.
4. No copied agent directory map or duplicated source parser.
5. Honest reporting about what upstream lock data can and cannot guarantee.

## Goals

- Provide project-local desired-state management through `skillstate.toml`.
- Support remote repositories, repository subpaths, refs, and local skill sources accepted by `skills`.
- Install selected skills into selected agents without interactive prompts.
- Generate deterministic plans before changing files.
- Reuse project `skills-lock.json` generated by `skills`.
- Support CI drift checks with meaningful nonzero exit codes.
- Preserve unrelated manually installed skills unless pruning is explicitly requested.
- Keep the package small and implementation understandable.
- Work on macOS, Linux, and Windows with supported Node.js versions.

## Non-Goals

- Building a skill registry or search index.
- Reimplementing Git cloning, skill discovery, or agent path resolution.
- Installing MCP servers, hooks, prompts, or full agent configurations in v1.
- Implementing transitive skill dependencies in v1.
- Claiming exact reproducibility when upstream lock data does not pin a commit.
- Automatically deleting unmanaged skills.
- Supporting global/user-level manifests in the first release.

## User Experience

### Installation

```bash
npx skillstate init
npx skillstate sync
```

Projects may pin the CLI as a development dependency:

```bash
npm install --save-dev skillstate
npx skillstate sync
```

Skillstate should depend on a compatible, pinned range of the `skills` package and execute its local binary. It should not run an unpinned `npx skills` subprocess that can change behavior between invocations.

### Core Commands

```text
skillstate init                 Create a starter skillstate.toml
skillstate sync                 Install missing or changed desired skills
skillstate sync --dry-run       Print plan without mutation
skillstate sync --prune         Remove lock entries absent from manifest after confirmation
skillstate check                Validate manifest and report drift; never mutate
skillstate list                 Show desired and installed state
skillstate add <source>         Add dependency, install it, update manifest
skillstate remove <name>        Remove dependency and its managed installation
skillstate update [name...]     Refresh selected dependencies intentionally
```

Common options:

```text
--agent <name...>               Override configured agents for this invocation
--copy                          Copy rather than symlink
--config <path>                 Use another manifest
--json                          Emit machine-readable output
--yes                           Skip confirmations
--verbose                       Include backend command and diagnostic details
```

### Exit Codes

```text
0  success / no drift
1  command or installation failure
2  invalid manifest or configuration
3  drift detected by check
4  backend compatibility failure
```

## Manifest Design

Default filename: `skillstate.toml` at the Git repository root.

```toml
schema = 1

[install]
agents = ["claude-code", "opencode"]
mode = "symlink"

[[sources]]
source = "vercel-labs/agent-skills"
ref = "main"
skills = [
  "react-best-practices",
  "web-design-guidelines",
]

[[sources]]
source = "anthropics/skills/skills/pdf"
skills = ["pdf"]

[[sources]]
source = "./skills/internal-review"
skills = ["internal-review"]
```

### Schema Rules

- `schema` is required and currently must equal `1`.
- `[install].agents` is a non-empty list of names passed through to `skills`.
- `[install].mode` accepts `symlink` or `copy`.
- Each `[[sources]]` entry requires `source`.
- `skills` accepts a non-empty list or `"*"`.
- `ref` is optional and converted to the `skills` fragment syntax (`source#ref`).
- Unknown keys fail validation by default to catch misspellings.
- Duplicate source/ref/skill combinations fail validation.
- Local paths resolve relative to the manifest directory, not process CWD.
- Manifest traversal stops at the Git root.

### Agent Preferences

Project configuration provides defaults, while developers can override targets without editing shared state:

```bash
skillstate sync --agent opencode
```

Agent names should be passed to `skills` for validation. Skillstate must not maintain its own agent directory table.

## State and Lock Semantics

### Upstream Lock

Project installs currently produce `skills-lock.json`. Skillstate should treat it as backend-owned state:

- Read it for planning and drift reporting.
- Never hand-edit or reserialize it.
- Let `skills add`, `skills remove`, and future native install commands update it.
- Validate supported schema versions before relying on fields.

### Reproducibility Limitation

The current upstream lock records source, ref, skill path, and computed content hash. Restore reconstructs the source and fetches the ref again; it does not reliably pin an exact commit or verify the previous hash before replacing content.

Therefore v1 terminology must be precise:

- `check` validates manifest-to-lock coverage and local drift where observable.
- `sync` restores declared state using current upstream behavior.
- Skillstate must not describe this as byte-for-byte frozen installation.

Potential v2 options:

1. Adopt stronger upstream lock semantics if `skills` adds commit pinning and integrity verification.
2. Add a separate `skillstate.lock` containing exact commits and integrity hashes.
3. Contribute strict lock behavior upstream rather than owning another format.

Option 1 or 3 is preferable because Skillstate should remain a frontend.

### Ownership and Pruning

Normal `sync` is additive and corrective. It does not delete lock entries absent from the manifest because those may be manually installed or managed by another tool.

`sync --prune` should:

1. Compute extra installed entries.
2. Show each proposed removal and target.
3. Require confirmation unless `--yes` is present.
4. Delegate removal to `skills`.
5. Refuse ambiguous removals when ownership cannot be established safely.

## Architecture

```text
src/
  cli.ts                 command definitions and process exit handling
  config.ts              discovery, TOML parsing, schema validation
  model.ts               normalized desired-state types
  planner.ts             pure desired-vs-installed diff
  lock.ts                read-only adapter for upstream lock schemas
  backend.ts             skills CLI capability and subprocess adapter
  manifest-editor.ts     deterministic add/remove edits
  output.ts              human and JSON renderers
  commands/
    init.ts
    sync.ts
    check.ts
    list.ts
    add.ts
    remove.ts
    update.ts
```

### Design Boundaries

- Config parsing and planning remain pure where possible.
- All subprocess execution goes through one backend adapter.
- Commands consume plans rather than constructing ad hoc subprocess arguments.
- Human output goes to stderr when JSON data is written to stdout.
- Backend command arguments are arrays passed to `spawn`, never shell strings.
- No user input is evaluated by a shell.

### Backend Capability Detection

The upstream CLI is evolving. Skillstate should detect supported commands and version rather than assume one permanent interface.

Initial compatibility strategy:

1. Resolve local `skills` package version.
2. Enforce tested semver range.
3. Prefer stable native commands when available.
4. Fall back only to explicitly tested experimental commands.
5. Fail clearly when no safe route exists.

Example operation mapping:

| Operation | Preferred backend behavior |
| --- | --- |
| Install selected source | `skills add <source> --skill ... --agent ... --yes` |
| Restore backend lock | Stable `skills install`, then `experimental_install` only when tested |
| Remove selected skills | `skills remove --skill ... --agent ... --yes` |
| Update | `skills update <skill...> --project --yes` where supported |

## Planning Model

Planner input:

```text
DesiredState + InstalledState + InvocationOverrides -> Plan
```

Plan actions:

```text
InstallSource
RestoreSkill
UpdateSkill
RemoveSkill
NoOp
Warning
Error
```

Every action should include:

- Source and selected skill names.
- Effective agents and install mode.
- Reason for action.
- Exact backend argument array where applicable.
- Whether action is destructive.

The same plan powers human display, JSON output, dry runs, tests, and execution.

## Manifest Editing

`add` and `remove` must avoid surprising whole-file rewrites. Before selecting a TOML library, prototype comment and formatting preservation.

Preferred behavior:

- Preserve comments and unrelated formatting.
- Insert sources deterministically.
- Sort skill names within entries.
- Collapse empty source entries after removal.
- Write atomically through a temporary file and rename.

If reliable format-preserving edits are not feasible in the initial release, ship `init`, `sync`, `check`, and `list` first. Do not silently destroy user formatting to advertise `add` and `remove` prematurely.

## Security

Skills become instructions for privileged agents, so manifests and locks must be treated as untrusted input.

- Never invoke subprocesses through a shell.
- Validate refs, source strings, agent names, and local paths before execution.
- Reject local paths escaping the project when policy requires project locality.
- Reject path traversal in selected skill names.
- Do not follow manifest-controlled output symlinks during local file operations.
- Show source and ref before installation.
- Require explicit confirmation for pruning.
- Avoid reading or printing secret values.
- Preserve backend authentication behavior rather than collecting credentials.
- Document that installing a skill executes no code through Skillstate but exposes its instructions and referenced assets to an agent.

## Testing Strategy

### Unit Tests

- Manifest discovery and Git-root boundaries.
- TOML validation and normalization.
- Ref and local-path conversion.
- Planner action generation.
- Lock schema compatibility.
- Backend argument construction.
- Exit code mapping.
- JSON output stability.

### Integration Tests

- Temporary Git repositories with fake manifests and locks.
- Stub `skills` executable recording argv and exit status.
- Successful multi-source synchronization.
- Partial backend failure with nonzero exit.
- Dry-run guarantees no mutation.
- Agent override behavior.
- Explicit pruning behavior.
- Windows and POSIX path handling.

### End-to-End Tests

- Install one small public skill into an isolated temporary project.
- Verify generated backend lock and expected skill directory.
- Run sync twice and verify idempotent plan.
- Remove or change manifest entry and verify drift output.

Network tests should be separate from deterministic default test runs.

### Quality Gates

- TypeScript strict mode.
- Formatting and lint checks.
- Unit and integration tests on supported Node.js versions.
- macOS, Linux, and Windows CI matrix.
- Package tarball smoke test invoking `npx`-style binary.
- Dependency and secret scanning.

## Delivery Milestones

### Milestone 0: Repository Foundation

- Initialize TypeScript ESM package.
- Select supported Node.js versions and package manager.
- Add formatter, linter, test runner, CI, and release skeleton.
- Document product scope and architectural decisions.

### Milestone 1: Read-Only Core

- Implement `skillstate.toml` discovery and parsing.
- Define normalized desired-state model.
- Read supported `skills-lock.json` schemas.
- Implement pure planner.
- Ship `check`, `list`, `--dry-run`, and `--json`.

Acceptance criteria:

- Invalid config fails with actionable diagnostics.
- Drift detection requires no network or mutation.
- Planner unit tests cover all action types.

### Milestone 2: Synchronization

- Add pinned `skills` dependency and backend adapter.
- Implement install actions and agent overrides.
- Add subprocess failure aggregation.
- Add isolated integration tests.
- Ship `sync` without automatic pruning.

Acceptance criteria:

- Fresh project installs declared skills non-interactively.
- Repeated sync produces no planned changes when state matches.
- Backend errors produce stable nonzero exits.

### Milestone 3: Lifecycle Commands

- Prototype format-preserving TOML edits.
- Implement `init`, `add`, `remove`, and `update`.
- Add explicit `sync --prune` with preview and confirmation.
- Improve global and per-command diagnostics.

Acceptance criteria:

- Manifest comments survive lifecycle operations.
- Destructive operations never occur implicitly.
- Update is the only normal command that intentionally moves refs.

### Milestone 4: Public Release Readiness

- Add full documentation and examples.
- Run package tarball and clean-machine tests.
- Publish prerelease to npm.
- Gather feedback against Claude Code, Codex, OpenCode, and Cursor projects.
- Publish `1.0.0` only after backend compatibility and config schema stabilize.

## Release and Repository Conventions

- Package name: `skillstate`.
- Binary name: `skillstate`.
- Default branch: `main`.
- Initial repository visibility: private.
- Commit conventional, focused changes.
- Use semantic versioning.
- Keep changelog from first public prerelease.
- Pin GitHub Actions by commit before public release.

## Open Decisions

Resolve during Milestone 0 or focused spikes:

1. Minimum Node.js version.
2. npm, pnpm, or another development package manager.
3. TOML parser/editor with acceptable formatting preservation.
4. Exact tested `skills` package range.
5. Whether v1 permits local sources outside the Git root.
6. Whether user-level agent overrides need a separate uncommitted config file.
7. Whether `update` operates by skill name, source, or both.
8. Whether upstream lock schema changes warrant a compatibility layer or strict version coupling.

## Success Measures

- A new teammate can clone a project and install declared skills with one command.
- CI can detect manifest/installation drift without mutating files.
- Skillstate adds no agent-specific installation paths of its own.
- A normal `skills` update does not require a Skillstate release unless its public CLI contract changes.
- Users can understand every planned mutation before approving it.
- Documentation accurately distinguishes repeatable desired state from cryptographically frozen dependencies.

## First Implementation Slice

The first code change after repository setup should be deliberately small:

1. Parse a minimal `skillstate.toml`.
2. Normalize sources and effective agents.
3. Emit the corresponding `skills add` argument arrays under `skillstate sync --dry-run`.
4. Test parsing and argument generation without network access.

This proves the core boundary before adding subprocess execution, lock inspection, or manifest mutation.
